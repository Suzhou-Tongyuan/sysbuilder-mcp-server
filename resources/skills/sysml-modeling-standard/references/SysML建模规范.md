# SysML建模规范（整合精简版）

> 本规范以项目已有的命名规范、图使用规范、模型元素使用规范为主体，结合 SysML 精粹强调的“模型为核心、图为视图、围绕问题建模”的思路，用于约束本工作区的 SysML 建模活动。

## 1. 总体要求

### 1.1 目的

统一需求分析、功能分析、架构设计、接口设计、参数分析与验证追溯中的建模方法，保证模型在命名、组织、图种选用、关系建立和审查要求上保持一致、清晰、可追溯、可维护。

### 1.2 适用范围

适用于：
- 系统级建模
- 分系统级建模
- 单机/设备级建模
- 外部系统与参与者建模
- 任务流程、作业流程、状态模式建模
- 接口、参数、约束与验证建模

### 1.3 建模基本原则

- 目的驱动：建模服务于工程问题求解，而不是为了画图而画图。
- 模型优先：图只是视图，核心是模型元素及其语义关系。
- 最小充分：只建立支撑分析、设计、沟通和验证所必需的模型。
- 分层细化：按系统层、分系统层、设备层逐层展开。
- 单一语义：需求、行为、结构、状态、参数各司其职，不混用。
- 可追溯：建立来源、需求、功能、结构、验证的基本闭环。
- 一致性：名称、定义、接口、参数和图间关系必须一致。

## 2. 命名规范与外观规范

### 2.1 命名原则

- 清晰：每个模型元素和模型图应避免歧义。
- 完备：需要命名的元素和图必须按规范命名。
- 简洁：关系类型已能表达语义时，避免多余命名。

### 2.2 图命名

- 图名建议使用中文。
- 图名按其表达对象命名。
- 结构图优先用名词或名词短语。
- 活动图优先用动词或动宾短语。

### 2.3 元素命名

- 模型元素建议使用中文命名。
- 用例、活动名称采用“动词 + 宾语”。
- 需求名称采用名词或名词性短语。
- 模块名称采用名词，不使用动作词。
- 参与者名称为人、角色或外部系统名称。
- 状态名称应是稳定状态名词，不是动作。

### 2.4 编码建议

关键元素建议采用统一编码：

`[类别缩写]-[层级]-[序号]-[名称]`

示例：
- REQ-SYS-001-任务准备要求
- ACT-SUB-003-执行点火
- BLK-SUB-002-控制分系统
- IF-EXT-006-遥测接口
- ST-SYS-004-故障隔离

常用缩写：
- 需求：REQ
- 用例：UC
- 活动：ACT
- 状态：ST
- 模块：BLK
- 接口：IF
- 参数：PAR
- 约束：CON
- 验证：VER / TC

### 2.5 布局要求

- 同图内元素字体、大小、风格尽量一致。
- 元素间距尽量均匀。
- 避免连线过长、过密、过多交叉。
- 连接关系要优先表达清楚语义，再考虑版式美观。

## 3. SysML 图使用规范

### 3.1 图种选择总则

按问题选图，不追求所有图种平均使用：
- 用例图：谁与系统交互，系统提供什么能力
- 需求图：系统必须满足什么，如何追溯
- 活动图：系统如何执行任务
- BDD/IBD：系统由什么组成，如何连接
- 状态机图：系统处于什么状态，何时迁移
- 参数图：参数和约束如何关联
- 时序图：对象之间如何按时间交换信息
- 包图：模型如何组织

### 3.2 模块定义图 BDD

用于说明系统静态结构。

允许重点表达：
- 模块
- 组成属性
- 引用属性
- 值类型
- 接口块
- 约束块

主要关系：
- 组成
- 引用
- 泛化

要求：
- 组成用于物理整体-部分关系
- 引用用于逻辑整体-部分关系
- 泛化用于分类与抽象-具体关系

### 3.3 内部模块图 IBD

用于说明模块内部组成部分之间的连接关系。

要求：
- 图中主体应为组成属性、引用属性
- 连接器连接端口
- 项目流表达流动的信息、能量或数据
- 信息流类型需与接口兼容

### 3.4 参数图

用于说明系统约束、性能关系和工程分析关系。

要求：
- 重点表达值属性、约束参数、绑定关系
- 适用于公式、约束、性能关系
- 不用于表达一般流程

### 3.5 需求图

用于展示需求及其追溯关系。

可表达关系：
- deriveReqt
- refine
- satisfy
- verify
- trace
- copy

要求：
- 每条需求至少包含 `id` 和 `text`
- 关键需求建议补充来源、层级、验证方式、状态、版本
- 需求描述应可验证，避免模糊词

### 3.6 包图

用于组织模型结构和命名空间。

可表达关系：
- 包含
- 导入
- 依赖

### 3.7 用例图

用于说明系统对外可见服务和参与者关系。

要求：
- 参与者在系统边界之外
- 用例在系统边界之内
- 用例表达系统能力，而不是内部实现动作
- `include` 表示必经子流程
- `extend` 表示条件触发的扩展能力

### 3.8 活动图

用于说明任务流程、功能分解和行为执行过程。

要求：
- 活动名采用“动词 + 宾语”
- 泳道优先按责任主体划分
- 顶层回答“总体怎么做”
- 中层回答“关键能力如何协同”
- 底层回答“动作如何执行”
- 应覆盖关键正常流程和异常流程
- 对象流应与接口模型保持一致

### 3.9 时序图

用于说明关键交互场景中的消息顺序。

要求：
- 聚焦关键交互，不要求所有流程都建图
- 消息名应与接收方操作或信号定义保持一致
- 生命线应与结构模型中的对象对应

### 3.10 状态机图

用于说明系统生命周期、工作模式和状态迁移。

要求：
- 状态名必须是稳定状态名词
- 转换应尽量明确事件、条件和动作
- 状态机图不替代流程图

### 3.11 矩阵与表格

适用于摘要表达关系和批量审查：
- 需求功能追溯矩阵
- 架构功能追溯矩阵
- 需求表格
- 架构表格

## 4. 模型元素使用规范

### 4.1 Block

Block 用于表达系统、分系统、组件及其静态结构特征。

可定义：
- 组成属性
- 引用属性
- 值属性
- 约束属性
- 端口

要求：
- 组成属性用于物理整体-部分
- 引用属性用于逻辑整体-部分
- 值属性用于量化特征
- 约束属性用于数学关系
- Block 名称使用名词

### 4.2 Constraint Block

用于定义数学关系、性能关系和工程分析约束。

重点：
- 约束参数由绑定的值属性提供数值
- 约束块优先用于重用

### 4.3 Actor

Actor 表达与系统交互的外部角色或外部系统。

要求：
- 只能位于系统边界外
- 不能用系统内部组成块替代参与者

### 4.4 Package

Package 用于分组和组织模型元素。

推荐顶层包结构：

```text
00_任务场景与利益相关方
01_用例模型
02_需求模型
03_行为模型
04_结构模型
05_接口模型
06_状态与模式模型
07_参数与约束模型
08_验证模型
09_追踪与分析
```

建议层级：

```text
L1_系统层
L2_分系统层
L3_设备层
```

### 4.5 Requirement

Requirement 至少包含：
- `id`
- `text`

要求：
- 不直接写成设计方案
- 应具备可验证性
- 关键需求标明来源、层级、验证方式和版本

### 4.6 Use Case

要求：
- 表达系统对外提供的能力
- 优先先建顶层总用例，再分解子用例
- 关键用例建议补充前置条件、后置条件、主流程、异常流程、关联需求

### 4.7 Action

Action 表示活动中的不可再分步骤。

要求：
- 语义单一
- 边界清晰
- 输入输出与对象流、接口保持一致

### 4.8 Activity Partition

用于表达责任分配。

要求：
- 同一张图内泳道划分依据应统一
- 不要在同一图中混用不同划分逻辑

### 4.9 Lifeline

用于时序图中的交互参与实体。

要求：
- 与结构模型对象保持一致

### 4.10 State

用于表达相对稳定的系统条件或运行模式。

要求：
- 状态名称使用状态名词
- 用于表达状态与迁移逻辑，不替代流程表达

## 5. 关系、分配与追溯规范

### 5.1 常用需求关系
- satisfy：由块元素/活动元素满足需求

### 5.2 功能分配

- 关键功能应分配到明确的结构承担者
- 避免存在大量无人承担的功能
- 可通过泳道、分配关系或矩阵体现

### 5.3 建议矩阵

- 需求功能追溯矩阵
- 架构功能追溯矩阵

### 5.4 建议表格视图

- 需求表格
- 架构表格

## 6. 建模流程建议

建模顺序：
1. 任务场景分析与用例图
2. 需求定义与需求图
3. 功能分析与活动图
4. 交互时序分析
5. 运行状态分析
6. 架构设计与 BDD
7. 内部交互设计与 IBD
8. 设计验证与参数图
9. 关系矩阵与追溯检查

## 7. 审查清单

完成前至少检查：
- 是否围绕明确问题建模
- 是否存在重复、无效或超范围图
- 命名是否统一且唯一
- 元素语义是否混用
- 图与模型库对象是否一致
- 接口和对象流是否一致
- 关键需求是否具备可验证性
- 是否建立了最小追溯闭环
